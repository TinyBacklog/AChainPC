# M4 60fps e resolução interna — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `fps60 = true` no `astralchain.ini` põe o jogo a 60fps com a jogabilidade e as
cutscenes à velocidade certa. `resolution_scale` sobe a resolução interna. Ambos funcionam
sem rebuild.

**Architecture:**
- **Patches no lifter, com toggle em runtime.** O `export_module` lê
  `<module>.patches` e o lifter emite `if (acre_fps60) { alternativa } else { original }`
  em cada ponto patchado. `acre_fps60` é uma variável C global, definida no frontend e
  posta pelo ini.
- Há dois tipos de patch:
  - `word`: troca uma instrução AArch64 por outra. Os bytes originais são verificados.
  - `hook`: chama uma função C antes da instrução. Se a função devolver 1, já definiu
    `c->pc` e o bloco termina.
- Os hooks vivem em `game/patches/fps60.c` e entram no `astralchain-static`.
- A resolução usa só o scaler do `video_core` (`resolution_setup` e `scaling_filter`).

**Tech Stack:** C (hooks e código gerado), C++20 (lifter e frontend), Python stdlib
(pipeline), clang `--target=aarch64-linux-gnu` como assembler para gerar e verificar as
codificações.

**Spec:** `docs/superpowers/specs/2026-10-14-astralchainre-design.md` (secção 7).

## Global Constraints

- Só se usam factos (endereços, semântica) do `AstralChain-Dynamic-FPS/docs/TECHNICAL.md`
  (sem licença). A lógica e as codificações são nossas. Não se copiam bytes nem código.
- Todos os endereços são offsets do `main` da 1.0.1, verificados contra os inputs dumpados:

  | Offset | Original (verificado) | Papel |
  |---|---|---|
  | `0x9E8D84` | `csinc w1, w8, wzr, ne` | intervalo de apresentação no arranque (modo 0→1, 1→2) |
  | `0x9DB6BC` | `csinc w1, w9, wzr, ne` | intervalo de apresentação em runtime |
  | `0x91DBDC` | `cbz x8, 0x91DCB4` | primeira amostra do timer |
  | `0x91DC10` | `cbz w21, 0x91DC48` | escolha entre o step fixo (cutscene) e o medido |
  | `0x48BE14` | `fcvtzs w8, s0` (x8 = timer) | contador até 30 |
  | `0x57E7DC` | `ldr s0, [x24, #0xd0]` | contador de paridade |
  | `0x57E7E0` | `fcvtzu w8, s0` | contador de paridade |

- Objeto timer (o `x19` em `0x91DBB0`):
  - `+0xC8` tick anterior;
  - `+0xD0` step (em frames de 30fps), float;
  - `+0xD4` resto, float;
  - `+0xD8` ticks inteiros deste frame (com fps60);
  - `+0xDC` ms→step (0.03);
  - `+0xE0` ms medidos;
  - `+0xE4` contador.
- O override de step (sincronização de áudio) é o float em `main+0xDADC5C`.
- Com `fps60 = false`, o comportamento é bit-a-bit o original. Os testes do lifter provam-no.
- Commits como `kadinho`, sem push.

## Review Focus

1. **Patch cujo `expected` não bate** (outra versão, ou offset errado). Esperado: o export
   falha com o offset e as duas palavras, em vez de gerar código errado (Task 1).
2. **Alternativa que é um branch** (`cbz w8, 0x57E810`). Esperado: o alvo e `pc+4` são
   inícios de bloco. Sem isso, há fallback para o JIT no primeiro frame a 60fps (Task 1).
3. **Toggle a meio do jogo** (o ini só é lido no arranque). Esperado: o valor fica fixo
   por sessão e isso está documentado no ini (Task 3).
4. **Step muito pequeno a framerates altos** (um monitor de 240Hz sem vsync). Esperado:
   o step é limitado a ≥ 1/16, para não haver divisões por ~0 (Task 2).
5. **Cutscene com override de áudio ativo.** Esperado: a duração a 60fps está dentro de
   ±2% da duração a 30fps (Task 4, manual).

### Task 2: Patch `fps60` do Astral Chain

**Files:**

  memória num array)
- Modify: `frontend/CMakeLists.txt` (compila o `fps60.c` no `astralchain-static`)

**Patches:**

| Offset | Tipo | Alternativa |
|---|---|---|
| `0x9E8D84` | word | `mov w1, #1` |
| `0x9DB6BC` | word | `mov w1, #1` |
| `0x91DBDC` | hook | `acre_fps60_first_sample` |
| `0x91DC10` | hook | `acre_fps60_step` |
| `0x48BE14` | word | `ldr w8, [x8, #0xd8]` |
| `0x57E7DC` | word | `ldr w8, [x24, #0xd8]` |
| `0x57E7E0` | word | `cbz w8, 0x57E810` |

**Lógica dos hooks** (nossa, escrita a partir da semântica):
- `first_sample(c)`: se `x8 != 0`, devolve 0 e o `cbz` original corre. Se não:
  - escreve `+0xD0 = 1.0f`, `+0xD4 = 0.0f`, `+0xD8 = 1`, `+0xE4 = 0`;
  - mete `c->pc = base + 0x91DCB4`;
  - devolve 1.
- `step(c)`:
  - `ms = f32[+0xE0]`, `step = ms * f32[+0xDC]`;
  - se `w21 != 0` e `f32[main+0xDADC5C] > 0`: `step *= override`;
  - `step = clamp(step, 1/16, 2)`;
  - `rem = f32[+0xD4] + step`, `ticks = floor(rem)`, `rem -= ticks`;
  - escreve `+0xD0 = step`, `+0xD4 = rem`, `+0xD8 = ticks` (u32), `+0xE4 = 0`;
  - mete `c->pc = base + 0x91DCB4` e devolve 1.

O `x19` é o objeto timer. A memória é lida e escrita por `c->host_mem->load/store`.

- [ ] **Step 1: Testes dos hooks (RED).** Cobrem:
  - 16.7 ms → step 0.5, ticks alternam 0/1;
  - 33.3 ms → step 1.0, tick 1;

  - 1 ms → clamp a 1/16;
  - override 0.9 com `w21 = 1` → step × 0.9;
  - override com `w21 = 0` → ignorado;
  - `first_sample` com `x8 = 0` e com `x8 != 0`.
